# Design: hotsmeta.kr — A Korean HotS Tier List That Matches Gut Feel

Generated by /office-hours on 2026-09-28
Branch: (no repo — new project)
Status: APPROVED 2026-09-28 (3 rounds of adversarial review 8/10 · 2 corrections from the owner · API v1 measured results reflected · Open Questions 1·2·3·7 closed). Remaining unknown = live `data[]` row fields.
Mode: Startup → during diagnosis "no revenue expectation (P3)" confirmed, designed as a community tool

## Context (Why build this)
The owner plays HotS mostly in Quick Match (QM) and said "it's inconvenient that there is no stats site." When measured, sites did exist (Heroes Profile tables, HOTS GG tiers). What is truly missing is three things: **QM tiers** (HOTS GG is Storm League only), **a public formula** (HOTS GG's "Meta Strength" is undisclosed and frequently moves opposite to win rate), and **Korean**. The "gap between gut feel and the screen" the owner felt was because (1) the mode was different, and (2) the formula is popularity-weighted. So what we build is **a Korean tier list that matches gut feel**. QM has no ban/pick — you pick a hero first, and only then are teammates and map decided. So the QM user's decision is just one: "which hero do I pick in this mode right now," and per-map tiers are used for decisions only in Storm League (draft). Publishing/customizing the formula is **lower priority** (the owner): most users only look at whether a reliable tier exists, and that trust comes not from accuracy but from **the absence of a gap with gut feel**. The formula is written as a single line as the basis for trust.

## Problem Statement
Korean HotS users (especially QM users) have no way to learn, within 30 seconds, "what's strong in QM right now" before picking a hero, or, for Storm League (SL) users, "what's strong on this map" during ban/pick. The existing tools are English-only, Storm League-only, with an undisclosed formula (HOTS GG), or are just number tables with no judgment (Heroes Profile, HotS Analytics KR). Community tier lists (Inven, Arca, FMKorea) are hand-drawn and leave only arguments.

## Demand Evidence (Q1)
- The owner himself: "It's hard to know which characters are good right now," "There are many maps, so I want to check right away during ban/pick." He actually didn't know HOTS GG existed → evidence it doesn't reach Korean users.
- Community: Arca "3 sites for checking HotS talents," FMKorea "the current HotS tier list at a glance," Inven tier list — people are searching for it and making it by hand.
- The Aichi (Overwatch YouTuber) video the owner shared: YouTubers sniping at each other over the tier formula (pick 7 : win 3 → pick·win·ban). Evidence that **the formula itself is content**.
- Missing evidence: money, named third-party users, return visits. → Set the success criterion as return visits.

Key measurements (Storm League, patch 2.55.17.98025, HP all ranks):
- HOTS GG tiers are not win-rate tiers. B = 47.0~53.7%, C = 46.1~53.1%, overlapping. Brightwing 47.6% (ban 34%) → B, Samuro 53.7% → B, Gazlowe 53.1% → C, Falstad 51.5% → S.
- Running the Aichi formula `pick×(WR−50)×3 + ban` on the same source gives the same tier as HOTS GG for **39/90**, with 12 differing by 2 or more tiers. Tiers are a choice of formula.
- Mode difference: Illidan SL 53.3 / QM 50.7, Brightwing 47.6 / 51.8, Abathur 50.6 / 53.3 (QM pick 35%), Azmodan 51.4 / 52.8 (QM #3). The QM sample is larger than SL (5,028 vs 3,511 per hero).
- Verifying the owner's gut feel: for Illidan the QM data sided with the owner; for Azmodan the opposite → the owner accepted the data with "I only saw our own games."

## Target User & Narrowest Wedge (Q3·Q4)
- **First user = the owner** (QM, soon Storm League). Next = the people hand-drawing tier lists on Arca/Inven.
- **Wedge = one page, QM overall tier list** (all maps, role filter). Toggling to Storm League brings up a map dropdown. The formula is one line under the table. Sliders, presets, draft simulator, talents, and accounts are cut.
- "Value even if you do nothing": open the link and the default is QM·all maps. No login.
- **Trust sensor**: per hero row, one press of "Does this match your gut feel? 👍 👎" (GoatCounter event, no server). Heroes with a large gap are the target of the next formula revision. To the user it's a signal that "your gut feel is reflected."

## Constraints

- The owner's code rules: Python 3.11+ · uv · pydantic-settings · structlog · async I/O · dataclass · TDD (/feature-workflow) · 80% coverage.
- Minimal operating cost. No server.

## Approaches Considered
### A. Static Lens (adopted)
Python collector (Actions cron) → JSON commit → static frontend (browser-side calculation). Effort **S~M** (phase 1 = collector + 1 tier list page + 👍👎 + tests on both sides; CC ~half a day. Sliders·hero page are phase 2) / Risk Low. No server·DB, snapshots = git history (separate branch).
### B. Service (FastAPI + Postgres + Next.js)
Scalable skeleton. Effort M / Risk Med. No feature needs a server right now → after the return-visit metric.
### C. Publish first, no site
Collector + manual image posting once a week. Fastest demand measurement, but the core experience (sliders·filters) is missing. → Absorbed as A's distribution channel.

### Collector (Python)
- **(09-28 update, after confirming the cap) phase 1 collection = 5 calls/day**: `/v1/heroes/stats` × `group_by_map=true` × {QM all, SL all, SL `league_tier=1,2`, SL `league_tier=3,4`, SL `league_tier=5,6`} — 35/70 per week. Serial, 60-second interval (group_by_map is 1 per minute), each 202 → poll. The patch list `/v1/patches` is separate (1,000,000/week). **Per-rank-bracket UI is phase 2**, but snapshots accumulate from day one (owner's decision). `latest/` is `qm.json, sl.json, sl_low.json(1-2), sl_mid.json(3-4), sl_high.json(5-6)`.
- (Old calculation, for reference) phase 1 combination = 3 calls/day: (1) 1 call to look up the current minor patch id (Open Q2 — if omitting `timeframe` defaults to the latest patch, this call is 0) + (2) `game_type` ∈ {Storm League, Quick Match} × all brackets × `group_by_map=true`, 2 calls. 21 calls/week, ≤42 including retries — within the Basic weekly cap (minimum 70). **SL rank brackets (HP `league_tier` 0–2 Bronze~Silver / 3–4 Gold~Plat / 5–6 Diamond~Master) are phase 2** — 3 more calls/day would be 42/week, 84 including retries, possibly exceeding the minimum cap → confirm the actual cap before phase 2.
- The "all maps" row is not a separate call but **derived by summing per-map wins/losses**. Match count = Σ(all heroes' games)/10 (10-player games; QM mirror picks slightly overstate, acceptable), pick% = games/matches×100, ban% = bans/matches×100 — the `group_by_map` response must include per-map bans (count or %) (included in Open Q2). QM has no bans, so pick% = popularity (confirmed identical by HP measurement).
- Identifying the current minor patch: the patch list call ((1) above). Patch change detection = this id ≠ `meta.json.current_patch`.
- **Patch change policy**: when a new patch is detected, **within the same run**, build the move of existing latest → previous and the new latest in tmp, then apply **as one rename set** (if the new patch call fails, nothing moves). Record `patch_started_at` in `meta.json`. On the frontend, **per mode**, if the share of heroes with n≥200 on the current patch is under 50%, that mode **shows the previous patch by default with a banner** ("패치 후 N일, 표본 적음 — 이전 패치 기준" (N days after patch, small sample — based on previous patch), N = today − patch_started_at) + toggle (`?patch=previous|current`).
- **Missing previous**: before the first patch change there is no `previous/` (`meta.previous_patch: null`). In that case both `?patch=previous` and the under-50% verdict show **the current patch + banner only** (no 404).
- **(1) Condition for skipping the patch call**: only when the `/Heroes/Stats` response includes the patch id (Open Q2). Otherwise (1) always runs — `current_patch`·`patch_started_at` come from there.
- **Atomicity**: replace `data/latest/` (and previous/) only when all calls succeed (tmp directory → rename). If any one fails, keep latest, exit≠0 → Actions opens an issue. Retry is 1 per call, **5xx·timeout only**; no retry on 429 (cap protection). During development, no API calls, fixtures only.
- Normalize responses into the `HeroStat` dataclass (hero, mode, map, wins, losses, games, bans, pick, popularity). Raw responses go gzipped to the `snapshots` branch as-is (raw immutable, derived mutable). If the API doesn't provide a win-rate CI, compute Wilson 95% on the frontend.
- structlog JSON logging; the token is never printed in logs·errors (absence asserted by test).
- **`latest/{qm,sl}.json` schema (the sole contract between collector ↔ formula.ts)**:
  ```json
  {"patch": "2.55.17.98025", "mode": "qm", "collected_at": "2026-09-28T09:20:53Z",
   "matches": 31600,
   "rows": [{"hero": "Illidan", "map": "all", "wins": 3435, "losses": 3342, "games": 6777, "bans": 0, "pick": 15.0, "popularity": 15.0},
            {"hero": "Illidan", "map": "Cursed Hollow", ...}]}
  ```
  `map: "all"` rows are derived and inserted by the collector. Win rate·CI·score are computed by the frontend. vitest fixtures are converted into this schema (the scratch `hp.json` is in web-parsed form and differs). The frontend fetch path is `import.meta.env.BASE_URL + 'latest/qm.json'` (the absolute path `/latest/…` breaks on Pages).

### Formula (web/src/formula.ts, displayed on screen as-is)
```
Units    : WR·pick·ban all in %p (0–100). The games-weighted average win rate is 50 by definition, so avg = 50 fixed.
n        = games (sample of the selected mode·map cell)
WRs      = 50 + (WR − 50) × n / (n + k)            # sample shrinkage, default k = 500
score    = pick × (WRs − 50) × w_pick + ban × w_ban  # default w_pick = 3, w_ban = 1 (Aichi)
QM       : ban = 0 → score = pick × (WRs − 50) × w_pick
n < 200  : "표본 부족" (insufficient sample) gray, no tier assigned, excluded from rank·cut denominators
Tiers    : only the n≥200 set, score descending, cumulative share cuts S 6% / A 24% / B 54% / C 82% / D 94% / F the rest
           boundary_i = min(N, max(floor(share_i × N), boundary_{i−1} + 1))  — monotonic, at least 1 per tier, with small N the later tiers empty out first
           (N=90: boundaries 5/21/48/73/84 → S 5·A 16·B 27·C 25·D 11·F 6)
```
- The phase 1 screen shows the formula as **one line** only: "티어 = 픽률 × (승률−50) × 3 + 밴률, 표본 200 미만은 제외. 데이터: Heroes Profile, 매일 갱신." (Tier = pick rate × (win rate−50) × 3 + ban rate; samples under 200 excluded. Data: Heroes Profile, refreshed daily.) A collapsed "자세히" (Details) shows the block above.
- **Phase 2** (after return-visit·👎 data): 3 presets (Aichi · additive (HOTS GG-style: (WRs−50) + 0.15×pick + 0.15×ban) · pure win rate) + sliders (w_pick, w_ban, k) + highlight of heroes whose tier changed + URL sharing. Internally, implement as parameters in `formula.ts` from phase 1 but hide only the UI (all tests are attached in phase 1).

## ⭐ API Measurements 2 — The Heroes Profile API has moved to v1 (2026-09-28)
- Root cause confirmed: `api.heroesprofile.com` is the **old API** (ends 2027-01-01); new keys don't work there (hence 401 + Last Used: Never). The old docs' `?api_token=` is also slated for deprecation.
- **New contract**: base `https://www.heroesprofile.com/api/external/v1`, header `Authorization: Bearer <key>`. Measured: `/heroes`·`/patches`·`/maps`·`/heroes/stats` all 200 (test data).
- **`/heroes/stats` parameters**: `timeframe_type` (minor|major|major_grouped) · `timeframe` (build/patch, comma-separated multiple) · `game_type` (`qm`,`sl`,`ud`,`ar`… comma-separated multiple) · `region` (NA/1, EU/2, **KR/3**, CN/5 — all regions if omitted) · `hero` · `role` · `game_map` · `hero_level` (band lower bounds 1,5,10,15,25,40,60,80,100) · `league_tier` (0 wood … 6 master, **7 all**; `hero_league_tier`·`role_league_tier` same) · `mirror` (0|1) · `groupsize` · `statfilter` (default win_rate, 37 kinds) · `group_by_map` (true|false) · `mode` (json|csv).
- **Response (200)**: `average_win_rate, average_confidence_interval, average_popularity, average_pick_rate, average_ban_rate, average_positive_influence, average_negative_influence, average_*_win_rate_change, average_games_played, data[]`. `data[]` row = `{name, short_name, hero_id, role, wins, …}` — test data fills only `wins` (5-hero placeholder). Actual row fields to be confirmed with the first live call (per the old docs losses·games_played·win_rate·popularity·ban_rate·pick_rate; since the averages have a CI, rows very likely have confidence_interval too).
- **202 job model**: on cache miss, `202 {job_id}` + `Location` + `Retry-After` (seconds). Poll by following Location (polling is free; the per-minute limit applies). Keep going while 202; on 200 that body is the result (no envelope). Handle `status: failed|not_found`. Cold queries take "minutes." **Once warmed, other callers also get 200 immediately.**
- **group_by_map=true**: the per-minute limit drops **60 → 1** (a query per map). Counted as 1 call (warning of a possible multiplier later). ⇒ The collector's QM·SL calls are **at least 60 seconds apart**, each 202 → poll.
- **Error envelope**: `{"error":{"code","message"}}`; 401 unauthenticated · 403 subscription_inactive/project_details_required/endpoint_not_in_plan… · 404 not_found · 422 invalid_parameters/missing_*/unknown_*/timeframe_unavailable/group_by_map_unsupported · 429 rate_limited/quota_exceeded(Retry-After) · 500. **Error responses are not charged.**
- **Test mode**: if the account is "Data mode = Test Data," fixed example responses, no quota deduction, limits apply. Switch to Live for real data. (If there had been an old key, it expires on the Live switch — not applicable to us.)
- **Old patches can't be queried** (`422 timeframe_unavailable`) — only what `/patches` provides. Test mode `/patches` latest is 2.55.17.97771 (live 98025 not visible — example data).
- Cap (confirmed): rolling 7-day allowance per endpoint. Heroes/Stats **70/week**. See screenshot `docs/hp-api-limits-basic-2026-09-28.png`.
- Value lists (90 heroes·19 playable maps·6 game_types·6 roles) saved as `docs/hp-api-v1-variables.md`.
