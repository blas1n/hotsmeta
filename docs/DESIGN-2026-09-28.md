## Context (왜 이걸 만드나)
형님이 빠대 위주로 히오스를 하며 "통계 사이트가 없어 불편하다"고 했다. 실측하니 사이트는 있었다(Heroes Profile 표, HOTS GG 티어). 진짜 없는 것은 셋이다: **빠대 티어**(HOTS GG 는 스톰 리그만), **공개된 공식**(HOTS GG 의 "Meta Strength"는 비공개고 승률과 자주 반대로 움직인다), **한국어**. 형님이 느낀 "체감과 화면의 괴리"는 (1) 모드가 달라서, (2) 공식이 인기 가중이라서였다. 그래서 만들 것은 **체감과 맞는 한국어 티어표**다. 빠대는 밴픽이 없다 — 영웅을 먼저 고르고 나서 팀원과 맵이 정해진다. 그러니 빠대 유저의 결정은 "지금 이 모드에서 어느 영웅을 고를까" 하나이고, 맵별 티어는 스톰 리그(드래프트)에서만 결정에 쓰인다. 공식 공개·커스텀은 **후순위**(형님): 대부분의 유저는 신뢰성 있는 티어가 있는지만 보고, 그 신뢰는 정확도가 아니라 **체감과의 괴리가 없는 것**이다. 공식은 신뢰의 근거로 한 줄만 적는다.

## Problem Statement
한국 히오스 유저(특히 빠대 유저)가 영웅 고르기 전에 "지금 빠대에서 뭐가 세냐"를, 스톰 리그 유저가 밴픽 중에 "이 맵에서 뭐가 세냐"를 30초 안에 알 방법이 없다. 있는 도구는 영어·스톰 리그 전용·공식 비공개(HOTS GG)거나, 숫자 표만 있고 판단이 없다(Heroes Profile, HotS Analytics KR). 커뮤니티 티어표(인벤·아카·에펨)는 손으로 그려 논쟁만 남는다.

## Demand Evidence (Q1)
- 형님 본인: "당장 뭐가 좋은 캐릭터인지 알기 어려워", "맵이 여러개라 밴픽 때 바로 확인". 실제로 HOTS GG 존재를 몰랐다 → 한국 유저에게 닿지 않는다는 증거.
- 커뮤니티: 아카 "히오스 특성보는 사이트 3개", 에펨 "한눈에 보는 현재 히오스 티어표", 인벤 티어표 — 사람들이 찾고 있고 손으로 만들고 있다.
- 형님이 준 아이치(오버워치 유튜버) 영상: 티어 공식(픽7:승3 → 픽·승·밴)을 두고 유튜버끼리 저격전. **공식 자체가 콘텐츠**라는 증거.
- 없는 증거: 돈, 이름 있는 제3자 유저, 재방문. → 성공 기준을 재방문으로 잡는다.

## Status Quo (Q2) — 실측 표
| 사이트 | 형태 | 티어 | 빠대 | 맵/구간 필터 | 공식 공개 | 한국어 |
|---|---|---|---|---|---|---|
| Heroes Profile | 표(WR·±CI·인기·픽·밴·Influence·게임수) | 없음 | 있음 | 있음 | n/a | 없음 |
| HOTS GG (HP 데이터 위) | S~F 티어 + 드래프트 시뮬 | 있음 | **없음** | 있음 | **없음** | 없음 |
| HotS Analytics (KR) | 표(게임수·승률) | 없음 | 있음 | 상세만 | n/a | 있음 |
| 인벤·아카·에펨 | 수제 | 주관 | — | — | — | 있음 |

핵심 실측 (Storm League, 패치 2.55.17.98025, HP 전랭크):
- HOTS GG 티어는 승률 티어가 아니다. B = 47.0~53.7%, C = 46.1~53.1% 로 겹친다. Brightwing 47.6%(밴 34%) → B, Samuro 53.7% → B, Gazlowe 53.1% → C, Falstad 51.5% → S.
- 아이치 공식 `픽×(승률−50)×3 + 밴` 을 같은 원본에 돌리면 HOTS GG 와 같은 티어 **39/90**, 2단계 이상 차이 12. 티어는 공식의 선택이다.
- 모드 차이: Illidan SL 53.3 / QM 50.7, Brightwing 47.6 / 51.8, Abathur 50.6 / 53.3(QM 픽 35%), Azmodan 51.4 / 52.8(QM 3위). QM 표본이 SL 보다 크다(영웅당 5,028 vs 3,511).
- 형님 체감 검증: Illidan 은 QM 데이터가 형님 편, Azmodan 은 반대 → 형님이 "우리 판만 봤다"로 데이터를 받아들임.

## Target User & Narrowest Wedge (Q3·Q4)
- **첫 유저 = 형님** (빠대, 곧 스톰 리그). 다음 = 아카/인벤에서 티어표를 손으로 그리는 사람들.
- **웨지 = 빠대 종합 티어표 한 페이지**(전체 맵, 역할 필터). 스톰 리그로 토글하면 맵 드롭다운이 생긴다. 공식은 표 아래 한 줄. 슬라이더·프리셋·드래프트 시뮬·특성·계정은 뺀다.
- "아무것도 안 해도 가치": 링크 열면 기본이 빠대·전체 맵. 로그인 없음.
- **신뢰 센서**: 영웅 행마다 "체감과 맞나요? 👍 👎" 한 번 누르기(GoatCounter 이벤트, 서버 없음). 괴리가 큰 영웅이 곧 다음 공식 수정의 대상이다. 유저에게는 "당신 체감을 반영한다"는 신호.

## Constraints
- 공식 API 없음. Heroes Profile API 유료(Basic $5/월, 60 calls/min, 주간 상한 엔드포인트군별). 리플레이엔 랭크가 없다.
- 형님 코드 규칙: Python 3.11+ · uv · pydantic-settings · structlog · async I/O · dataclass · TDD(/feature-workflow) · 커버리지 80%.
- 운영비 최소. 서버 없음.

## Premises (형님 확인)
1. (수정) 가치는 **체감과 맞는 빠대 티어 + 한국어**. 모드를 맞추고(빠대/스톰 리그) 공식이 인기 가중으로 승률을 뒤집지 않으면 체감과 맞는다. 공식 공개는 한 줄, 커스텀은 2차. 맵별은 스톰 리그에서만. — 형님 정정 반영
2. 데이터는 HP API. **리플레이 직접 수집 안 함**, 일일 스냅샷 영구 보관으로 대체. — 처음 "병행"이었다가 2차 의견(콜드스타트 1년+, MMR 부재) 뒤 A 로 결정
3. 수익 기대 없음. 커뮤니티 도구. — 동의

## Cross-Model Perspective (Claude 서브에이전트, 대화 미열람)
- 스틸맨: "공식을 보여주는 한국어 HotS 메타 대시보드" — 티어를 함수로 취급하는 유일한 사이트. 만들 것은 데이터가 아니라 렌즈.
- 핵심 한 줄: QM 이 표본은 더 큰데 아무도 서비스 안 함. 첫 화면 = QM. 핵심 루프 = **감 교정**(재방문 이유).
- P2 반박: 업로더 분포·콜드스타트(셀 90×15×2×4, 셀당 200 → 리플레이 21.6만 ≈ 1년+)·**MMR 은 리플레이에 없어 구간 뷰 불가**. 대안 = 일일 스냅샷 캐시. 증명 = 업로드 버튼 4주 후 주간 고유 업로더 <50.
- 48h 프로토타입: Actions cron → HP API → JSON → 정적 사이트, 페이지 2, 공식 공개, 측정 = 7일 재방문 ≥ 첫날의 20%.
- **내 불일치**: 제안된 기본 공식 `(WRs−50)+0.15pick+0.15ban` 은 덧셈이라 Brightwing 을 A 로 올린다(HOTS GG 와 같은 실패). 기본은 **곱셈형**(아이치)으로 가고, 덧셈형은 프리셋으로 둔다.

## Approaches Considered
### A. 정적 렌즈 (채택)
Python 수집기(Actions cron) → JSON 커밋 → 정적 프론트(브라우저 계산). Effort **S~M**(1차 = 수집기 + 티어표 1페이지 + 👍👎 + 양쪽 테스트; CC ~반나절. 슬라이더·영웅 페이지는 2차) / Risk Low. 서버·DB 없음, 스냅샷 = git 히스토리(별도 브랜치).
### B. 서비스 (FastAPI + Postgres + Next.js)
확장 뼈대. Effort M / Risk Med. 지금 서버가 필요한 기능이 없다 → 재방문 지표 뒤로.
### C. 사이트 없이 게시부터
수집기 + 이미지 주 1회 수동 게시. 수요 측정 최속이나 핵심 경험(슬라이더·필터) 부재. → A 의 배포 채널로 흡수.

## Recommended Approach — A. 정적 렌즈

### 수집기 (Python)
- **(09-28 갱신, 상한 확인 후) 1차 수집 = 5콜/일**: `/v1/heroes/stats` × `group_by_map=true` × {QM 전체, SL 전체, SL `league_tier=1,2`, SL `league_tier=3,4`, SL `league_tier=5,6`} — 주 35/70. 직렬, 60초 간격(group_by_map 분당 1), 각 202 → 폴링. 패치 목록 `/v1/patches` 는 별도(1,000,000/주). **구간별 UI 는 2차**지만 스냅샷은 첫날부터 쌓는다(형님 결정). `latest/` 는 `qm.json, sl.json, sl_low.json(1-2), sl_mid.json(3-4), sl_high.json(5-6)`.
- (옛 계산, 참고용) 1차 조합 = 3콜/일: (1) 현재 minor 패치 id 조회 1콜(Open Q2 — `timeframe` 생략 시 최신 패치가 기본이면 이 콜은 0) + (2) `game_type` ∈ {Storm League, Quick Match} × 구간 전체 × `group_by_map=true` 2콜. 주 21콜, 재시도 포함 ≤42 — Basic 주간 상한(최저 70) 안. **SL 랭크 구간(HP `league_tier` 0–2 브론즈~실버 / 3–4 골드~플래 / 5–6 다이아~마스터)은 2차** — 추가 3콜/일이면 주 42, 재시도 포함 84 로 최저 상한 초과 가능 → 2차 전에 실제 상한 확인.
- "전체 맵" 행은 별도 콜이 아니라 **맵별 wins/losses 합산으로 파생**. 매치 수 = Σ(전 영웅 games)/10 (10인 게임; QM 미러픽은 미세 과대, 허용), pick% = games/매치수×100, ban% = bans/매치수×100 — `group_by_map` 응답에 맵별 bans(count 또는 %)가 와야 한다(Open Q2 에 포함). QM 은 밴이 없으므로 pick% = popularity (HP 실측으로 동일 확인).
- 현재 minor 패치 식별: 패치 목록 콜(위 (1)). 패치 변경 감지 = 이번 id ≠ `meta.json.current_patch`.
- **패치 교체 정책**: 새 패치 감지 시 **같은 실행 안에서** 기존 latest → previous 이동과 새 latest 구성을 tmp 에서 만든 뒤 **한 rename 집합으로** 반영(새 패치 콜이 실패하면 아무것도 안 움직인다). `meta.json` 에 `patch_started_at` 기록. 프론트는 **모드별로** 현재 패치의 n≥200 영웅 비율이 50% 미만이면 그 모드는 **이전 패치를 기본으로 띄우고 배너**("패치 후 N일, 표본 적음 — 이전 패치 기준", N = 오늘 − patch_started_at) + 토글(`?patch=previous|current`).
- **previous 부재**: 최초 패치 교체 전엔 `previous/` 가 없다(`meta.previous_patch: null`). 그때는 `?patch=previous` 도, 50% 미만 판정도 **현재 패치 + 배너만** 띄운다(404 없음).
- **(1) 패치 콜 생략 조건**: `/Heroes/Stats` 응답에 패치 id 가 포함될 때만(Open Q2). 아니면 (1)은 항상 실행 — `current_patch`·`patch_started_at` 이 거기서 나온다.
- **원자성**: 모든 콜 성공 시에만 `data/latest/`(및 previous/) 교체(tmp 디렉터리 → rename). 하나라도 실패하면 latest 유지, exit≠0 → Actions 가 이슈를 연다. 재시도는 콜당 1회, **5xx·timeout 만**, 429 는 재시도 금지(상한 보호). 개발 중엔 API 를 안 부르고 픽스처만.
- 응답을 `HeroStat` dataclass(hero, mode, map, wins, losses, games, bans, pick, popularity) 로 정규화. 원본 응답은 gzip 으로 `snapshots` 브랜치에 그대로(원본 불변, 파생 가변). 승률 CI 는 API 가 안 주면 프론트에서 Wilson 95% 로 계산.
- structlog JSON 로깅, 토큰은 로그·에러에 절대 안 찍는다(테스트로 부재 단언).
- **`latest/{qm,sl}.json` 스키마 (수집기 ↔ formula.ts 유일 계약)**:
  ```json
  {"patch": "2.55.17.98025", "mode": "qm", "collected_at": "2026-09-28T09:20:53Z",
   "matches": 31600,
   "rows": [{"hero": "Illidan", "map": "all", "wins": 3435, "losses": 3342, "games": 6777, "bans": 0, "pick": 15.0, "popularity": 15.0},
            {"hero": "Illidan", "map": "Cursed Hollow", ...}]}
  ```
  `map: "all"` 행은 수집기가 파생해 넣는다. 승률·CI·score 는 프론트가 계산. vitest 픽스처는 이 스키마로 변환해 둔다(스크래치 `hp.json` 은 웹 파싱 형태라 다르다). 프론트 fetch 경로는 `import.meta.env.BASE_URL + 'latest/qm.json'` (절대경로 `/latest/…` 는 Pages 에서 깨진다).

### 공식 (web/src/formula.ts, 화면에 그대로 표기)
```
단위     : WR·pick·ban 모두 %p (0–100). 게임수 가중 평균 승률은 정의상 50 이므로 avg = 50 고정.
n        = games (선택한 모드·맵 셀의 표본)
WRs      = 50 + (WR − 50) × n / (n + k)            # 표본 수축, 기본 k = 500
score    = pick × (WRs − 50) × w_pick + ban × w_ban  # 기본 w_pick = 3, w_ban = 1 (아이치)
QM       : ban = 0 → score = pick × (WRs − 50) × w_pick
n < 200  : "표본 부족" 회색, 티어 미부여, 순위·컷 분모에서 제외
티어     : n≥200 집합만 score 내림차순, 누적 비율 컷 S 6% / A 24% / B 54% / C 82% / D 94% / F 나머지
           경계_i = min(N, max(floor(비율_i × N), 경계_{i−1} + 1))  — 단조, 티어마다 최소 1명, N 이 작으면 뒤 티어부터 빈다
           (N=90: 경계 5/21/48/73/84 → S 5·A 16·B 27·C 25·D 11·F 6)
```
- 1차 화면엔 공식 **한 줄**만: "티어 = 픽률 × (승률−50) × 3 + 밴률, 표본 200 미만은 제외. 데이터: Heroes Profile, 매일 갱신." 접힘 "자세히"에 위 블록.
- **2차**(재방문·👎 데이터 뒤): 프리셋 3개(아이치 · 덧셈(HOTS GG 류: (WRs−50) + 0.15×pick + 0.15×ban) · 순승률) + 슬라이더(w_pick, w_ban, k) + 티어 바뀐 영웅 하이라이트 + URL 공유. 내부 구현은 1차부터 `formula.ts` 에 파라미터로 두되 UI 만 숨긴다(테스트는 1차에 다 붙는다).

## ⭐ API 실측 2 — Heroes Profile API 는 v1 로 이사했다 (2026-09-28)
- 원인 확정: `api.heroesprofile.com` 은 **옛 API**(2027-01-01 종료), 새 키는 거기서 안 된다(그래서 401 + Last Used: Never). 옛 문서의 `?api_token=` 도 폐기 예정.
- **새 계약**: base `https://www.heroesprofile.com/api/external/v1`, 헤더 `Authorization: Bearer <key>`. 실측: `/heroes`·`/patches`·`/maps`·`/heroes/stats` 모두 200(테스트 데이터).
- **`/heroes/stats` 파라미터**: `timeframe_type` (minor|major|major_grouped) · `timeframe` (빌드/패치, 콤마 복수) · `game_type` (`qm`,`sl`,`ud`,`ar`… 콤마 복수) · `region` (NA/1, EU/2, **KR/3**, CN/5 — 생략 시 전 리전) · `hero` · `role` · `game_map` · `hero_level` (밴드 하한 1,5,10,15,25,40,60,80,100) · `league_tier` (0 wood … 6 master, **7 all**; `hero_league_tier`·`role_league_tier` 동일) · `mirror` (0|1) · `groupsize` · `statfilter` (기본 win_rate, 37종) · `group_by_map` (true|false) · `mode` (json|csv).
- **응답(200)**: `average_win_rate, average_confidence_interval, average_popularity, average_pick_rate, average_ban_rate, average_positive_influence, average_negative_influence, average_*_win_rate_change, average_games_played, data[]`. `data[]` 행 = `{name, short_name, hero_id, role, wins, …}` — 테스트 데이터는 `wins` 만 채워 줌(5영웅 플레이스홀더). 실제 행 필드는 라이브 첫 콜로 확정(옛 문서 기준 losses·games_played·win_rate·popularity·ban_rate·pick_rate, 평균에 CI 가 있으니 행에도 confidence_interval 있을 가능성 큼).
- **202 잡 모델**: 캐시 미스면 `202 {job_id}` + `Location` + `Retry-After`(초). Location 을 따라 폴링(폴링은 무료, 분당 리밋은 적용). 202 동안 계속, 200 이면 그 본문이 결과(봉투 없음). `status: failed|not_found` 처리. 콜드 쿼리는 "분 단위". **한 번 데워지면 다른 호출자도 즉시 200.**
- **group_by_map=true**: 분당 리밋이 **60 → 1** 로 떨어진다(맵마다 쿼리). 콜 수는 1로 계산(추후 배수 가능성 경고). ⇒ 수집기의 QM·SL 두 콜은 **60초 이상 간격**, 각각 202 → 폴링.
- **에러 봉투**: `{"error":{"code","message"}}`; 401 unauthenticated · 403 subscription_inactive/project_details_required/endpoint_not_in_plan… · 404 not_found · 422 invalid_parameters/missing_*/unknown_*/timeframe_unavailable/group_by_map_unsupported · 429 rate_limited/quota_exceeded(Retry-After) · 500. **에러 응답은 과금 안 됨.**
- **테스트 모드**: 계정 "Data mode = Test Data" 면 고정 예시 응답, 쿼터 미차감, 리밋은 적용. Live 로 바꾸면 실제 데이터. (옛 키가 있었다면 Live 전환 시 만료 — 우리는 해당 없음.)
- **오래된 패치는 조회 불가**(`422 timeframe_unavailable`) — `/patches` 가 주는 것만. 테스트 모드 `/patches` 최신은 2.55.17.97771(라이브 98025 는 안 보임 — 예시 데이터).
- 상한(확정): 엔드포인트별 롤링 7일 allowance. Heroes/Stats **70/주**. 스크린샷 `docs/hp-api-limits-basic-2026-09-28.png` 참조.
- 값 목록(hero 90명·맵 19개 playable·game_type 6·role 6)은 `docs/hp-api-v1-variables.md` 로 저장.

### 설계에 미치는 변경
1. 수집기 클라이언트: base URL·Bearer·**202 폴링 루프**(Retry-After 준수, 상한 예: 15분) 추가. 재시도는 5xx/timeout 만, 429 는 Retry-After 만큼 대기 후 1회.
2. 두 group_by_map 콜은 직렬 + 60초 간격. 하루 총 소요 = 콜드면 수 분.
3. "전체 맵" 파생 유지. `region=KR` 은 **표본 크기 실측 후 결정**(KR 만 쓰면 표본이 줄어 n<200 회색이 늘 수 있다 → 기본은 전 리전, KR 은 2차 토글 후보).
4. 패치 목록은 `/v1/patches`(키 필요, general allowance) — `valid_globals: true` 인 최신 빌드를 고른다.
5. 개발·테스트: 계정 Test Data 모드에서 계약 개발 → 라이브 전환 후 첫 콜로 행 스키마 확정 → 픽스처 갱신.
